# nftables module

The nftables module implements the `router.Implementor` interface by controlling
nftables on the ingress device.
Its only job is managing nftables DNAT rules.

## Architecture

Each ingress service creates two nftables chains:

| Chain prefix | Hook       | Type   | Priority | Purpose                             |
|--------------|------------|--------|----------|-------------------------------------|
| `ingress_`   | PREROUTING | NAT    | -110     | DNAT from external IP to pod IP     |
| `forward_`   | FORWARD    | Filter | -10      | Accept post-DNAT traffic in forward |

Priority `-110` is chosen to run before fw4's default `dstnat` chain (`-100`).

Each service also has a `postrouting` chain (MASQUERADE) shared across all services.

## Chain naming

Names are generated by `chainName()`: `{prefix}_{safe_service_key}`, truncated to
32 bytes.
Invalid nftables characters (`/`, `-`) are replaced with `_`.

## Rule structure

### Ingress (PREROUTING DNAT)

A rule matches the external destination IP + L4 protocol + destination port, then
performs DNAT.
Two strategies based on destination count:

- **Single destination**: `Immediate` loads + `NAT` expression
- **Multiple destinations**: nftables integer→(IP,port) map with `numgen incremental`
  for round-robin (`addLBMapNamed`)

### Forward (FORWARD accept)

Each destination gets two accept rules:

- **Forward** direction: match `daddr` + `dport`
- **Reply** direction: match `saddr` + `sport`

## Interface matching note

`iifname` matching is intentionally omitted.
In the PREROUTING hook, the kernel may report the physical parent interface rather
than the MACVLAN alias, causing rules to be silently skipped.
Matching on the unique destination IP is sufficient and interface-agnostic.

## State reconciliation

`rulesNeedUpdate()` compares desired state against existing nftables rules before
applying changes.
It checks: chain existence, rule count, per-target IP/proto/port matches (including
destination element sets for multi-dest targets), and trailing accept rule presence.

If rules are up to date, the `AddRules` call is a no-op — no flush occurs.

## Build tags

| File               | Tag      | Notes                                      |
|--------------------|----------|--------------------------------------------|
| `nftables.go`      | `linux`  | Real nftables netlink connection           |
| `nftables_stub.go` | `!linux` | No-op stubs (macOS/dev compilation)        |
| `helpers.go`       | _none_   | Shared constants, chain naming, validation |

The stub validates the service config via `validateService()` even on non-Linux
platforms to catch misconfiguration at development time.

## Thread safety

The `Manager` holds a `sync.Mutex` that guards all nftables `Conn` operations (`AddRules`,
`RemoveRules`).
The `ListRules` method does not lock (it is a stub).

## Key internals

- **`findTable()` / `ensureTable()`**: look up or create the `homelab_ingress` table
- **`ensurePostrouting()`**: creates the shared MASQUERADE chain if absent
- **`removeServiceChain()`**: deletes associated LB map sets, then the chain, in
  a single flush
- **`findChainAndRules()`**: fetches a chain and its rules, propagating errors

## Expression builders

| Function                 | Purpose                                       |
|--------------------------|-----------------------------------------------|
| `matchExprs`             | IP + proto + dport match (ingress)            |
| `matchIPDstExprs`        | Payload+Cmp for destination address           |
| `matchIPSrcExprs`        | Payload+Cmp for source address                |
| `matchProtoPortExprs`    | Meta+Cmp for L4 proto + Payload+Cmp for dport |
| `matchProtoSrcPortExprs` | Meta+Cmp for L4 proto + Payload+Cmp for sport |
| `dnatSingleExprs`        | Immediate+Immediate+NAT for single-dest DNAT  |
